# Stale inventory form protection

The previous product row lock made audit entries accurately describe each preceding write, but still permitted an older open form to overwrite a newer saved edit. Actual built-app HTTP requests against disposable PostgreSQL reproduced that overwrite. The previous action also accepted forms without a version and did not return a new version after save; all three new HTTP assertions failed before the repair.

Inventory forms now carry a SHA-256 fingerprint of the editable fields: name, category, description and published status. The server computes the current fingerprint while holding the existing row lock. A different submitted snapshot is refused before any product or audit write, unless the requested values already exactly match the saved values (a harmless retry). Missing/malformed fingerprints are rejected. Successful saves return the new fingerprint. This is conflict detection, not an authorization token; existing session and brand checks remain required. Equal editable values after an intervening change are intentionally equivalent, and unrelated product fields do not cause false conflicts.

The open editor keeps its initial fields and snapshot across server refreshes. Successful saves advance the snapshot; validation errors retain the submitted snapshot. A conflict message asks the user to copy edits and reload, with a reload button. Closing and reopening the editor loads current server props. The full-page reload discards unsaved edits, so the instruction to copy them is explicit.

Three new HTTP/database cases verify stale refusal, fresh save/new fingerprint and missing-version refusal. The controlled concurrent test now expects one winner for distinct edits from the same snapshot and one matching audit; identical concurrent edits still create one audit. A JSDOM interaction regression proves that server refreshes do not silently advance an open form's baseline, save does advance it, validation failure preserves it, and reopening uses current props.

Validation: 23 total built-app HTTP/PostgreSQL cases (9 inventory, 9 import, 2 concurrency, 3 stale), 13 component/parser/auth tests, the owned-server collision/cleanup check, four migrations, lint without warnings, Next type generation, TypeScript and production build pass. Bundled Next server-action guidance was read under AGENTS.md. Tests use fictional data, owned listeners and a new PostgreSQL17 fixture. Exact-head CI, publication and fixture cleanup are recorded in the PR/checkpoint.

No schema, credential, expiry policy, live service, merge or deployment changes. This does not add per-user/per-brand permissions to the shared pilot login, field-level merging, force overwrite, a full browser acceptance journey or live publication/provider validation. The unexposed visibility-toggle helper still serializes its read/write but has no browser form or snapshot protocol; this repair covers the exposed inventory editor.
